# attn-experts-moe — MoE с двумя типами экспертов: FFN + разреженное внимание

Реализация идеи: **в MoE-трансформере экспертами становятся не только FFN, но и
блоки (разреженного) внимания; роутер под каждый токен собирает свою команду
экспертов**. Проект сделан как исследовательский каркас: можно сравнивать
варианты компоновки и виды attention-экспертов на одной задаче.

## Идея

В стандартном MoE-трансформере (Mixtral, DeepSeek, Qwen-MoE...) слоистая
структура такая: `attention (плотный, общий) -> router -> top-k FFN-экспертов`.
Разреженным является только FFN-подслой.

Здесь проверяются два расширения:

1. **Sequential (JetMoE-style)** — два MoE-подслоя в блоке:

```
x → LN → [router₁: top-kₐ attention-экспертов] → +res
  → LN → [router₂: top-k_f FFN-экспертов]       → +res
```

2. **Mixed («один пул, два типа»)** — один роутер над общим пулом, но с
   **типовыми квотами**: под каждый токен выбирается ровно `{ffn: k_f, attn: k_a}`
   лучших экспертов каждого типа:

```
x → LN → MixedMoE( token → {attn-эксперт №7 (w=0.6), ffn-эксперт №2 (w=0.4)} ) → +res
```

То есть буквально «под каждый токен собирается экспозиция разных разреженных
вниманий + FFN».

## Attention-эксперт: два варианта

### `independent` — независимый sparse-attention эксперт *(основной, твоя версия)*

Каждый attention-эксперт — самостоятельная мини-группа голов со своими
`Wq/Wk/Wv/Wo` и **собственным паттерном разрежения**:

| pattern | что делает |
|---|---|
| `dense` | полный causal-attention |
| `window` | causal sliding-window (окно задаётся; у экспертов в пуле окна разные — смесь масштабов) |
| `topk` | на каждую строку запроса остаются только top-k ключей по score |

Тонкий момент, из-за которого JetMoE выбрал другой путь: если токен `i`
маршрутизирован к эксперту `e`, его запросу всё равно нужны K/V **всех**
позиций. Решение здесь честное: выбранный эксперт считает K/V плотно по всей
последовательности, но Q и выходную проекцию — только для маршрутизированных
строк. Экономия ~2× на Q/O против «плотной группы голов», а главное —
настоящая потокенная разреженность смеси. В коде есть оба пути исполнения:
точный (`forward_selected`, только выбранные строки) и батчевый fast-path
(`forward_batch`) — математически идентично для выбранных строк.

### `projection` — JetMoE-style (для сравнения с published-базлайном)

Эксперты — это куски проекций: каждый выдаёт свою долю Q,K,V (1/top_k от
размерности), выбранные срезы конкатенируются в порядке ранга роутера, дальше
**один общий** attention-кернел. Разреженность только в проекциях.

## Структура проекта

```
src/
  router.py    TopKRouter: uniform top-k ИЛИ типовые квоты; Switch aux-loss + z-loss
  experts.py   FFNExpert, AttentionExpert (dense/window/topk), ProjectionMoEAttention
  moe.py       SparseMoE: диспетчеризация пула (FFN — плоско, AttentionExpert — послежовательно)
  block.py     DualMoEBlock: layout='sequential' | 'mixed'
  model.py     TinyCausalLM (demo-scale causal LM)
tests/test_all.py   формы, строгая каузальность, отсутствие утечки за окно,
                    точность квот mixed, градиенты, генерация
train_demo.py       smoke-train: задача копирования [src|SEP|src]
results/            demo_results.json, baseline_long.log
```

Запуск:

```bash
python3 tests/test_all.py                 # 10 тестов
python3 train_demo.py --steps 500         # сравнение 3 конфигураций
python3 train_demo.py --configs mixed_independent --pattern topk --steps 800
```

## Результаты smoke-обучения (задача копирования)

Задача: `[src | SEP | src]` — чтобы предсказать вторую половину, нужно
ходить вниманием через разделитель (дистанция ~seq_len/2). Пол униграммы
≈ ln(V)=2.77; полностью решённое копирование ≈ 1.39 (шумная половина непредсказуема).
Окно внимания по умолчанию = seq_len//2+8, т.е. задача физически достижима.

d_model=128, 4 слоя, 8 FFN-экспертов (top-2), 4 attn-эксперта (top-2),
CUDA, одинаковый seed/init. Логи: `results/*.log`, `results/demo_results.json`.

| конфигурация | шагов | final CE | динамика |
|---|---|---|---|
| sequential + independent (твоя идея) | 500 | 1.74 | **самый быстрый разгон**: спуск начался до шага 200 |
| sequential + independent | 1600 | 1.61 | вышла на плато выше пола |
| sequential + projection (JetMoE-like) | 1600 | **1.3975 ≈ пол** | медленный старт (~шаг 400–600), но дорешала до пола |
| mixed + independent, raw-probs веса | 1600 | 2.687 (=пол) | не взлетела |
| mixed + independent, `--renorm-typed` | 800 | 2.687 (=пол) | ренормализация весов не помогла |
| mixed + independent, dense-паттерн | 800 | 2.687 (=пол) | разрежение внимания ни при чём |
| mixed + independent, lr=3e-3 | 800 | 2.687 (=пол) | learning rate ни при чём |

Выводы (в рамках toy-масштаба: одна задача, один seed):

1. **Независимые attention-эксперты учатся быстрее всех** — индукционный
   контур находится за <200 шагов, тогда как projection-варианту нужно
   в ~3 раза больше шагов на разгон. Механическое объяснение: у независимого
   эксперта запрос ходит по K/V только своего эксперта — координировать
   роутинг q- и k-сторон не нужно; в projection-режиме Q и K/V токена
   приходят от независимо выбранных срезов, и рано в обучении q·k между
   «несовместимыми» экспертами — шум (JetMoE училась на ~100B токенов,
   где это окупается).
2. **Но к финальному качеству projection догнал и перегнал** на этом бюджете:
   1.3975 против 1.61. Быстрый старт ≠ лучший итог.
3. **Mixed («один пул, два типа») устойчиво не взлетел**: 6 прогонов
   {raw-probs, renorm} × {window, dense} × {lr 1e-3, 3e-3} — все на униграммном
   полу. Это самый интересный негативный результат. Механика корректна:
   квоты точны, градиенты доходят во все эксперты, ветка внимания живая и
   чувствительна к контексту внутри окна (проверено тестами и зондами) —
   т.е. вопрос именно в оптимизационной динамике. Кандидаты на объяснение:
   (а) в sequential блоке «внимание → FFN» идут последовательно, и
   индукционному контуру это естественно, а в mixed они параллельны внутри
   одного блока; (б) ветка внимания делит residual-слот с FFN-ветками и
   получает ~⅓ сигнала (на инициализации чувствительность к контексту ~5×
   ниже, чем у sequential). Гипотезы, не доказательства.

Честные оговорки: demo-scale, одна задача, один seed; это sanity-check
механики и генератор гипотез, а не вывод о превосходстве в целом;
fast-path тратит FLOPs на невашированные строки (обмен на отсутствие тысяч
мелких kernel-launch'ей), точный путь тоже реализован и проверен тестом
эквивалентности.

## Проверка на реальном тексте (tiny Shakespeare, посимвольно)

Все модели обучены на одних данных, 500 шагов (~6.5 млн символов), d=128
(у «равного» плотного базлайна d=180). Полные логи: `results/lm_full.log`,
`results/dense_big.log`, примеры: `results/sample_*.txt`.

| модель | ошибка на отложке ↓ | перплексия ↓ | параметров всего / работает на токен | скорость обучения |
|---|---|---|---|---|
| обычный трансформер (малый) | 2.222 | 9.2 | 1.12M / 1.12M | 43K симв/сек |
| **обычный трансформер (равен MoE по объёму работы)** | **2.095** | **8.1** | 2.18M / 2.18M | 38K симв/сек |
| **наша идея** (эксперты внимания+FFN) | 2.139 | 8.5 | 7.42M / **2.18M** | ~4.6K симв/сек |
| JetMoE-стиль (эксперты-проекции) | 2.271 | 9.7 | 6.63M / 1.92M | ~6K симв/сек |

Что это говорит честно:

* **Механика работает**: обе MoE-модели учатся на реальном тексте и генерируют
  осмысленный шекспировидный текст (диалоги, имена персонажей, структура строк);
  разрежение и маршрутизация корректны (12 автотестов).
* **На этом масштабе плотная модель всё ещё лучше**: при равном объёме
  работы на токен (2.18M активных параметров) обычный трансформер даёт меньшую
  ошибку И учится в ~9 раз быстрее по стеночным часам. Это ожидаемо: при
  d=128 накладные расходы на диспетчеризацию экспертов съедают выгоду от
  пропуска 75% параметров. Выгода MoE проявляется на больших размерах,
  где матрицы толстые (все большие открытые модели — Mixtral, DeepSeek — MoE).
* **Среди MoE-вариантов наш — лучший**: 2.139 против 2.271 у JetMoE-стиля
  при том же бюджете, плюс быстрый разгон (см. предыдущий раздел).

Критерий практического успеха, который стоит проверять дальше: при одинаковом
ВРЕМЕНИ обучения (не числе шагов) sparse-версия должна обходить плотную,
или при равном качестве быть быстрее. На toy-масштабе это пока не так.

## Диспетчеризация и скорость: честные замеры

Как работает диспетчер (как в продакшн-системах): все пары «токен→эксперт»
сортируются по id эксперта, каждый эксперт получает сплошной кусок токенов и
обрабатывает его одной матричной операцией, один scatter-add собирает вклады.
На слой — одна синхронизация с хостом (границы кусков).

Эволюция скорости (полная модель, d=128, seq=256, batch=32, CUDA):

| версия диспетчера | мс/шаг moe_indep |
|---|---|
| наивная (nonzero на каждого эксперта) | 1335 |
| сегментная сортировка (текущая) | **856** |

Почему всё равно медленнее плотной модели на игрушечном масштабе (5–6×):

1. **Эксперты внимания здесь дороже плотного внимания**: каждый выбранный
   эксперт считает K/V всей последовательности → при 4 экспертах внимание
   стоит ~4× FLOPs плотного. Это фундаментальная цена схемы «независимые
   attention-эксперты»; JetMoE-стиль (общий кернел) её избегает.
   Чистые FFN-эксперты экономят как положено (top-2 из 8 = 25% FLOPs).
2. **Тонкие матрицы**: при d=128 GEMM каждого эксперта мал, GPU недогружен;
   накладные расходы видны только здесь и исчезают при d≥2048.
3. **Общие веса экспертов не запакованы**: в продакшне веса всех экспертов
   лежат одним тензором и обрабатываются grouped-GEMM ядром (Megablocks,
   Tutel); здесь стекование весов каждый форвард добавляет трафик.
4. Замеры сделаны на GPU, который делится с 4 чужими процессами — каждая
   синхронизация обходится дороже обычного.

Вывод для практики: «в разы быстрее» у MoE появляется при больших масштабах
(тысячи токенов на эксперта, упакованные grouped-GEMM ядра, bf16,
экспертный параллелизм) — поэтому все большие открытые модели MoE. На
игрушечном стенде корректно мерить не скорость, а качество на единицу
вычислений на токен — см. таблицу выше.

## Смесь механизмов смешивания: окна + линейное внимание (DeltaNet-стиль)

Идея «почему бы Mamba/DeltaNet-подобным механизмам тоже быть экспертами»
реализована прототипом: `LinearAttentionExpert` — каузальное линейное
внимание (накопительная ассоциативная память, O(T·d²)), ставится в один пул
с оконными экспертами (`--kinds window,window,linear,linear`).

Копирование через разделитель, 400 шагов, одинаковый бюджет:

| состав пула внимания | final CE |
|---|---|
| **2 оконных + 2 линейных (после фикса нормировки)** | **1.90** — лучше однородных! |
| 4 оконных эксперта | 2.00 |
| 4 линейных | 2.67 (=пол) |
| 2+2 ДО фикса (выходы не нормированы) | 2.62 |

Найденный по пути баг и урок: первый вариант линейного эксперта не имел
нормировки состояния — его выход разрастался до |7310| против ~0.4 у оконных
и **глушил всю смесь** (роутер был не виноват). Лечится знаменательной
нормировкой (как в Katharopoulos/RetNet). После фикса гетерогенный пул
обогнал однородный: линейным экспертам достаётся своя часть токенов, где
«размытая память» полезнее точечного поиска.

Диагностика роутера (`exp_routing.py`): доля линейных держится ~50–57% и с
aux-балансировкой, и без неё — маршрутизация приходит в локальное равновесие
«каждому типу — свои токены», а не в глобально-оптимальный состав.
Поведенческий тест подтверждает: при большой мгновенной разнице способностей
(эксперт-в-себя против эксперта-в-контекст) роутер предпочтение осваивает.
Практический вывод: разнородные пулы требуют сопоставимых масштабов выходов
и/или прогрева; тогда смесь работает и выигрывает.

## Иерархическое «дёшево -> выбор -> уточнение» (ветка hier-refine-attention)

Прототип идеи: (1) дешёвая проекция контекста в лендмарки по блокам;
(2) поточный каузальный гейт выбирает top-k прошлых блоков для каждого токена
(роутер читает проекцию, не скрытое состояние); (3) точное внимание только к
выбранным блокам + петля уточнения с фиксированным V (K/V считаются один раз,
Q-проекция пересчитывается). Код: `src/hier.py`, эксперимент `exp_hier.py`,
тесты `tests/test_hier.py` (5/5, включая строгую каузальность).

Копирование через разделитель, T=128 (дистанция 65), 600 шагов:

| внимание | CE | открытых блоков | параметры |
|---|---|---|---|
| плотное | 2.59 | 100% | 1.08M |
| **иерархическое** | **2.52** | **33%** | 1.28M |

Иерархическое точнее при трети открытых ключей (лендмарк-путь работает как
дешёвый канал глобального смешивания). Честные оговорки: стеночное время
пока НЕ экономится -- маска подаётся в плотный SDPA, нужна блочно-разреженная
реализация; параметров чуть больше; на T=256 обе модели в этом бюджете не
выходят из униграммного пола -- нужен более длинный прогон.

Найденные при отладке утечки каузальности (поучительно): гейт не должен
скорить лендмарк собственного блока (в нём есть будущее блока), резюме блока
запросов не должно усреднять весь блок, а мягкая поправка градиента обязана
браться из МАСКИРОВАННЫХ скоров. Все три канала закрыты, тест ловит каждый.

## Близкие работы

| Работа | Что общего / отличие |
|---|---|
| [MoA: Mixture of Attention Heads (Zhang et al., 2022)](https://aclanthology.org/2022.emnlp-main.278/) | первая «разреживать внимание по токенам»: роутер выбирает головы per token. Наши attention-эксперты = обобщение: целые группы голов + свои паттерны разрежения. |
| [JetMoE (2024)](https://arxiv.org/abs/2404.07413) | MoE и во внимании, и в FFN (8 экспертов, top-2). Отличие: их attention-эксперты — срезы проекций (общий кернел); здесь дополнительно есть вариант с независимыми sparse-паттернами. Конфиг `sequential_projection` воспроизводит этот дизайн. |
| [MoE++ (ICLR 2025)](https://arxiv.org/abs/2407.04853) | разные ТИПЫ экспертов в одном пуле (zero-computation, self-scaled...). Наш `mixed` — та же идея, но тип = «внимание vs FFN». |
| [Switch Transformer](https://arxiv.org/abs/2101.03961) | aux load-balancing loss (реализован) |
| Mixtral | renorm softmax по выбранным экспертам (флаг `norm_topk_prob`) |
| [DeepSeek-V2](https://arxiv.org/abs/2405.04434) | shared expert — плотный «дежурный» эксперт плюс роутеруемые (флаг `shared_expert=True`) |
| Longformer/Mistral | sliding-window как паттерн разрежения внутри attention-эксперта |

## Куда развивать

- RoPE вместо обучаемых позиций + KV-cache для генерации;
- capacity factor / dropping вместо dropless scatter;
- expert parallelism (all-to-all);
- сравнить `mixed` c `--renorm-typed` (ренормализация softmax по объединённым
  выбранным экспертам vs сырые вероятности) и без;
- разные паттерны у экспертов одного пула уже поддержаны (`make_attn_pool`
  делает ступенчатые окна) — исследовать mixture-of-patterns осознанно;
- большая задача (language modeling на реальном корпусе) для честного
  сравнения sequential vs mixed vs projection.
